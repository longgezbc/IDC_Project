# 接口升级需求：待审核进度日志列表分页

> 需求方：Android 客户端
> 涉及接口：`GET /tasks/progress/pending`
> 优先级：中（客户端审核页已完成分页改造，接口就绪后即可联调）
> 预计改动范围：TaskProgressController / TaskProgressService（仅此一个接口）

---

## 一、背景

待审核进度日志当前为**一次性全量返回**，无分页参数：

```kotlin
// 客户端现有定义（ApiService.kt L162-166）
@GET("tasks/progress/pending")
suspend fun getPendingProgress(
    @Query("projectId") projectId: Long? = null
): ApiResponse<List<ProgressLogDto>>
```

随着填报量增长，一次拉全量存在性能与流量问题（单条记录含 `images` 数组，体积较大）。
客户端其余 8 个列表接口均已采用统一分页协议，仅此接口未对齐。

## 二、升级方案

### 1. 请求：新增两个可选 Query 参数

```
GET /tasks/progress/pending?pageNum=1&pageSize=20&projectId=10001
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `pageNum` | Integer | 否 | `1` | 页码，从 1 开始 |
| `pageSize` | Integer | 否 | `20` | 每页条数，建议上限校验 ≤ 100（超过按 100 处理） |
| `projectId` | Long | 否 | - | 项目筛选（保留现有能力，不传查全部） |

### 2. 响应：`data` 由 `List` 改为分页对象

与项目现有分页协议保持一致（`PageResult`，MyBatis-Plus `IPage` 结构）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "records": [
      {
        "id": "1945009514945228800",
        "taskId": "1945009514945228801",
        "taskName": "A栋3层桥架安装",
        "projectId": "10001",
        "projectName": "XX数据中心一期",
        "progress": 65,
        "previousProgress": 50,
        "remark": "本期完成桥架200米",
        "images": ["/files/progress/2026/08/img_001.jpg"],
        "actualStartDate": "2026-08-01",
        "actualEndDate": "2026-08-10",
        "reviewStatus": "pending",
        "reviewerId": null,
        "reviewerName": null,
        "reviewTime": null,
        "reviewRemark": null,
        "reporterId": "10086",
        "reporterName": "张三",
        "reportTime": "2026-08-16T09:30:00"
      }
    ],
    "total": 57,
    "size": 20,
    "current": 1,
    "pages": 3
  }
}
```

**`data` 字段说明**（`records` 元素结构与现有 `ProgressLogDto` 完全一致，不改字段）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `records` | Array | 当前页数据，可为空数组（无待审核时 `[]`，`total=0`） |
| `total` | Long | 符合条件的总记录数 |
| `size` | Long | 每页条数（回显实际生效值，如超限被修正为 100 时返回 100） |
| `current` | Long | 当前页码 |
| `pages` | Long | 总页数（`total=0` 时为 `0`） |

### 3. 排序要求

保持现有排序不变（建议按 `reportTime` 或 `id` 倒序，最早的待审核排最前，便于按时间顺序审核）。**分页期间排序字段必须稳定**，否则翻页可能出现重复/漏记录。

### 4. 约束与边界

- 只返回 `reviewStatus = pending` 的记录（与现状一致，勿变）
- `pageNum` 超出 `pages` 时返回空 `records`，不算错误
- `pageNum`/`pageSize` 传非法值（0、负数、非数字）按默认值处理，不报错

## 三、兼容性说明

**此变更为破坏性更新**（`data` 类型由数组变为对象）。两点建议二选一：

1. **直接改**（推荐）：客户端与本接口只有审核页一处调用，客户端侧已就绪，后端上线后客户端同版本发版即可，无需保留旧格式；
2. 如后端短期内需新旧并行：加请求参数 `paged=true` 区分——不传参维持旧 `List` 格式，传 `paged=true` 返回新分页格式。客户端随后切换到 `paged=true`。

## 四、客户端联动

接口上线后，客户端改动（仅 `ApiService.kt` 一处 + `ReviewScreen.kt` 的 ViewModel 增加分页状态）预计半天内完成并发版，后端无需等待客户端同步。

## 五、验收用例（联调对照）

| 用例 | 请求 | 预期 |
|---|---|---|
| 首页 | `pageNum=1&pageSize=20` | `records` ≤ 20 条，`current=1`，`total/pages` 正确 |
| 中间页 | `pageNum=2&pageSize=20`（total=57） | `records` = 17 条，`current=2` |
| 超尾页 | `pageNum=99` | `records=[]`，`total` 不变，`code=200` |
| 空数据 | 无待审核记录 | `records=[]`，`total=0`，`pages=0`，`code=200` |
| 项目筛选 | `projectId=10001` | 只含该项目的待审核记录，`total` 为该项目计数 |
| 参数容错 | `pageNum=0&pageSize=-1` | 按默认 `1/20` 处理，不报错 |
| 排序稳定性 | 连续翻 3 页 | 记录不重复、不遗漏，合计 = `total` |
